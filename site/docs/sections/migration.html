Migrating from Pico

Moving a site from Pico CSS 2.1.1 to femto 3.0 changes file names, class and custom property names, builds, Sass settings, color schemes, and supported browsers.

femto 3.0 is derived from Pico CSS 2.1.1, copyright 2019-2024 Pico, under the MIT License (see LICENSE.md). It keeps every element and feature of Pico's default build, its 20 theme colors, its options, and its color utilities, rewritten as plain CSS with femto names.

New file names and URLs

Pico 2.1.1 femto 3.0
npm @picocss/pico npm @leoherzog/femto
Composer picocss/pico None; use npm, a CDN, or the download
css/pico.min.css, css/pico.css dist/femto.min.css, dist/femto.css
css/pico.colors.min.css, css/pico.colors.css dist/femto.colors.min.css, dist/femto.colors.css
css/pico.<color>.min.css dist/femto.min.css, then css/themes/<color>.css
The classless and fluid classless builds, with or without a color dist/femto.min.css, plus a theme file for a color; see Dropped builds below
The conditional builds None; see Dropped builds below

The one-file builds moved from css/ to dist/, and css/femto.css is now the @import entry. On jsDelivr, this link:

<link rel="stylesheet" href="https://cdn.jsdelivr.net/npm/@picocss/pico@2/css/pico.min.css">

becomes:

<link rel="stylesheet" href="https://cdn.jsdelivr.net/npm/@leoherzog/femto@3/dist/femto.min.css">

Until 3.0.0 is released, @3 does not resolve: write the version that Quick start gives in its place, in theme and combine URLs too.

If your <link> has an integrity attribute, it holds the hash of Pico's file, and the browser blocks femto's. Remove the attribute, or link an exact version of femto and write that file's hash, which is sha384- and the output of:

openssl dgst -sha384 -binary femto.min.css | openssl base64 -A

A themed build such as pico.jade.min.css becomes femto plus css/themes/jade.css, as two <link> tags or one combine URL:

<link rel="stylesheet" href="https://cdn.jsdelivr.net/npm/@leoherzog/femto@3/dist/femto.min.css">
<link rel="stylesheet" href="https://cdn.jsdelivr.net/npm/@leoherzog/femto@3/css/themes/jade.css">

Find and replace

Replace pico with femto in class names and custom properties, in your HTML, CSS, and scripts. femto has no --pico-* aliases, so every name needs the change:

  • Custom properties: --pico-primary becomes --femto-primary, and every other --pico- name likewise.
  • Color utility classes: .pico-color-jade-500 becomes .femto-color-jade-500, and .pico-background-* becomes .femto-background-*.

Change file paths, URLs, and package names by the table above, not by find and replace. Data attributes keep their names: data-theme, data-tooltip, and data-placement.

Dropped builds

The conditional builds (pico.conditional*.css) are gone. They styled what is inside .pico, and also set the root element's colors and typography, box-sizing on every element, the body's margin, and .container and .grid anywhere. femto styles the whole page, or a shadow root that loads it (see Shadow roots). Remove the .pico classes.

Without a conditional build, femto also styles everything that was outside .pico: the rest of the page, another framework's markup, and elements that scripts add to <body>, such as a chart's tooltip. To keep femto off a part of the page, load femto in a cascade layer and roll that part back in the same layer:

@import url(dist/femto.min.css) layer(femto);

@layer femto {
  :is(.not-femto, .not-femto *, #no-such-id) {
    all: revert-layer;
    box-sizing: border-box;
    background-repeat: no-repeat;
  }
}

The id matches nothing: it lifts the rule above femto's own rules, such as those on input:not([type=checkbox], [type=radio]). The last two lines keep what the conditional builds set on every element.

A shadow root that loads femto is not a drop-in for .pico either: its host takes femto's root background, text color, and font, its scheme follows the host's own data-theme, not the page's, and the page's rules no longer reach the content inside (see Shadow roots).

The classless builds (pico.classless*.css and pico.fluid.classless*.css), which made the <header>, <main>, and <footer> directly inside <body> containers on their own, are gone. Load femto and give those three a container class: .container for centered widths, or .container-fluid for the full width (see Container). A header, main, or footer nested in another element was never a container, so give it no class.

The classless builds' containers were body > header, body > main, and body > footer, at specificity (0,0,2), so a later rule of yours on one of those selectors won. .container and .container-fluid are (0,1,0), and now win over it for width, side margins, and side padding, and .container for maximum width too. If your CSS sizes those elements, add the class to your selectors, such as body > main.container, and compare the layout at every breakpoint.

Sass settings

femto has no Sass. Each Pico 2.1.1 setting is now a file, a custom property, or gone:

Pico 2.1.1 femto 3.0
$theme-color css/themes/<color>.css, after femto. Azure is built in. See Themes.
$enable-responsive-spacings: true css/options/responsive-spacings.css
$enable-responsive-typography: false css/options/fixed-typography.css
$enable-transitions: false css/options/no-transitions.css
$modules A custom module set
$breakpoints Fixed at 576, 768, 1024, 1280, and 1536px
$css-var-prefix Gone: always --femto-
$semantic-root-element Gone: always body
$enable-semantic-container, $enable-viewport Gone with the classless builds: give the header, main, and footer directly inside <body> (or your $semantic-root-element) the class .container, or .container-fluid where $enable-viewport was false
$enable-classes Gone: classes are always on
$enable-important Gone: femto keeps the default build's !important declarations
$parent-selector Gone with the conditional builds
pico.colors settings Gone: femto.colors.css is a static file

Map a setting only where it had an effect. $enable-responsive-spacings and $enable-responsive-typography worked through Pico's themes/default module, so if your $modules turned that module off, they did nothing: load no responsive-spacings.css, and load fixed-typography.css unless your own theme scaled the root font size.

Any other change is a custom property override on :root, after femto, such as :root { --femto-border-radius: 0; } (see CSS variables). Sass palette variables such as $azure-550 are custom properties in femto.colors.css, such as var(--femto-color-azure-550) (see Colors). A custom property has no value until the page renders, so a Sass color function such as mix() or rgba() cannot take one, and neither can an SVG in a data URI. Write the color's hex value there, which is the same as in Pico 2.1.1, or use CSS color-mix(in srgb, …).

If your own Sass reads Pico's Sass, such as @use "@picocss/pico/scss/settings", replace what it reads with the values: --femto- for $css-var-prefix, and for $breakpoints the breakpoints 576, 768, 1024, 1280, and 1536px, whose viewport widths are 510, 700, 950, 1200, and 1450px.

If your project still builds with Sass, @use "pkg:@leoherzog/femto"; includes dist/femto.min.css. A pkg: URL needs Sass's Node package importer: pass --pkg-importer=node to the sass command, or importers: [new NodePackageImporter()] to its JavaScript API. Without the importer, @use "@leoherzog/femto/dist/femto.min.css"; works with node_modules as a load path. Do not @use css/femto.css: Sass leaves its @imports as they are, and they would not resolve from your output file.

Load theme, option, and color files with @use too, after femto and before your own rules:

@use "pkg:@leoherzog/femto";
@use "pkg:@leoherzog/femto/css/themes/jade.css";
@use "pkg:@leoherzog/femto/css/options/fixed-typography.css";
@use "pkg:@leoherzog/femto/dist/femto.colors.min.css" as femto-colors;

The as keeps the colors file's namespace from clashing with femto's. Do not @import these files in Sass, which leaves an @import of a .css file as it is and moves it above femto.

Color scheme changes

Color tokens are now declared once, and data-theme sets the scheme instead of redeclaring the color tokens (see Color schemes). That changes six things:

  • data-theme on a button, heading, or form field keeps that element's own colors in the chosen scheme. In Pico 2.1.1 such an element took the page's background and text colors: on a dark page, <button data-theme="light"> was a white box that turned blue on hover.
  • data-theme="dark" on a web component's host now makes its shadow root dark when the component loads femto there (see Shadow roots). Pico 2.1.1, loaded only in the shadow root, gave it no color tokens.
  • Custom color overrides now work on plain :root and reach inside data-theme elements. In Pico 2.1.1, the light and automatic dark scheme selectors outranked :root, and every nested data-theme element redeclared the tokens. Likewise, your rules that set --femto-form-element-focus-color on a checkbox or radio take effect from specificity (0,1,1), where Pico 2.1.1 needed (0,2,1) or (0,3,1). To give a token a value per scheme, set its new --femto-light-* and --femto-dark-* pair on :root, such as --femto-light-primary and --femto-dark-primary, if it has one: the Pair column in Tokens says which do. A pair name for a token without one, such as --femto-primary-background, does nothing, so set that token itself to light-dark() of the two values (see CSS variables).
  • A rule of yours that redeclares color tokens for one scheme, under [data-theme=light], :root:not([data-theme=dark]), or @media (prefers-color-scheme: dark), still applies once renamed. Its values now also reach every data-theme element inside, of either scheme. Move each value to its token's pair on :root instead, or to light-dark() on a token without one. A :root:not([data-theme=dark]) rule also applied in automatic dark mode: to keep that, give the dark side its value too.
  • femto's colors follow each element's color-scheme, so a color-scheme that your own CSS sets now switches femto's colors there. In Pico 2.1.1 it switched only the browser's own controls. On the root or a data-theme element, it can also win over data-theme (see Color schemes). Remove such rules, or keep them off data-theme elements, as :root:not([data-theme]) does.
  • For a color token declared with light-dark() or set from one with var(), such as --femto-primary, getPropertyValue() now returns light-dark(...) text, where Pico 2.1.1 returned a color. To read the color in effect, see CSS variables.

Supported browsers

Pico 2.1.1 supported every browser in browserslist's defaults. femto 3.0 supports the browsers in Browser support, and drops the -ms- rules, ::-webkit-input-placeholder, and ::-moz-list-bullet. Browsers without light-dark() get only femto's light scheme and are not tested, so stay on Pico 2.1.1 if you need full support in them.

Other changes

  • In Firefox, elements that set no outline of their own, such as video and tooltips with tabindex, show the keyboard focus ring again, and a field the user has left invalid shows the focus and aria-invalid rings, as in Chrome and Safari. femto drops 2.1.1's :-moz-focusring { outline: none } and :-moz-ui-invalid { box-shadow: none }.
  • femto drops 2.1.1's reset rules that repeat what browsers already do: display: block on main, figure, and details, overflow: visible on button, svg:not(:root) { overflow: hidden }, and [dir=rtl] { direction: rtl }. A rule of your own for one of those properties that 2.1.1's reset overrode, such as button { overflow: hidden } in a stylesheet loaded before it, now applies: remove it, or restore the reset after femto.
  • Headings balance their lines (text-wrap: balance), so they often break at different words than in 2.1.1, and a heading inside an element with white-space: nowrap now wraps. To keep 2.1.1's breaks, add :is(h1, h2, h3, h4, h5, h6) { text-wrap: inherit; } after femto.
  • Some rendering bugs of 2.1.1 are fixed, such as an indeterminate <progress> that looked complete in Firefox with reduced motion. The changelog lists them.
  • The focus ring of role="group" and role="search" inside a data-theme element follows that element's scheme.
  • With no-transitions.css, --femto-transition is 0s (2.1.1 kept 0.2s ease-in-out; see Options), so your own rules that read it stop animating too, and the group focus ring no longer fades.
  • One other new token: --femto-grid-template-columns (see Grid).
  • The accordion and dropdown chevrons and the loading spinner are CSS masks. On filled buttons they take the button's text color. Your own background-image on them now shows only through the mask's shape, and a filter of yours still applies, over the new color: remove both, and set mask and background-color instead. A --femto-icon-chevron or --femto-icon-loading of your own sets only the shape of these icons, and the colors in its SVG are ignored, except in a select's chevron, which is still a background image. Color a mask icon with background-color, in a rule at least as specific as femto's, such as [aria-busy=true]:not(input, select, textarea, html, form)::before.
  • If your build ran rtlcss or postcss-rtlcss over Pico, keep femto out of it. femto mirrors itself in right-to-left text (see RTL), and a tool that flips its rules again puts the select, search, and validation icons on the text's side of the field.
  • If you used a classless build, classes such as .grid, .secondary, .dropdown, and .striped that it ignored are now styled.

Every difference from Pico 2.1.1 that the parity tests found is registered, with its reason, in tests/divergences/, and the changelog lists the changes in each release.
